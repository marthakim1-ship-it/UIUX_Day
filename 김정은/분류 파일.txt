# [YOVIA] Reference Classification & Validation Config

## 0. 이 파일의 역할

이 문서는 완료된 YOVIA 레퍼런스 리서치 결과를 읽어 다음 작업을 수행하는 별도 분류 지시서다.

1. 중복 사이트 탐지와 중복 그룹 생성
2. 중복 그룹별 대표 사이트 선정
3. `핵심 필요`
4. `부분 참고`
5. `불필요`
6. 디자인 적합도 평가
7. UX 적합도 평가
8. 총점과 우선순위 산정
9. 최종 추천 사이트 선정
10. 분류 결과 검수

이 파일은 **외부 웹사이트를 다시 조사하지 않는다.** 반드시 `research/REFERENCE_RESEARCH.txt`에 이미 기록된 내용과 P번호 근거만 사용한다.

다음 행위는 금지한다.

- 외부 웹 검색 또는 사이트 재열람
- 리서치 원본 파일 수정
- 확인되지 않은 사실 추정
- 점수를 맞추기 위한 임의 보정
- 단순 취향만으로 분류 변경
- 원본 레이아웃·카피·그래픽의 직접 복제 권장

---

## 1. 실행 준비와 명령어

### 1.1 파일 읽기와 대기

작업 폴더를 CLI 에이전트의 활성 워크스페이스로 연 뒤 아래 문장을 입력한다.

```text
@YOVIA_REFERENCE_CLASSIFICATION_CONFIG_V2.md를 처음부터 끝까지 읽고, research/REFERENCE_RESEARCH.txt와 research/progress.txt의 존재 여부 및 완료 상태만 확인하라. 아직 분류를 시작하지 말고, 입력 수량·평가 기준·출력 경로·검수 규칙만 점검한 뒤 "분류 실행 대기 중"이라고 답하라.
```

### 1.2 작업 제어 명령어

에이전트가 `분류 실행 대기 중`이라고 답한 뒤 다음 다섯 개 명령어만 작업 제어 명령으로 사용한다.

```text
실행
일시정지
재개
중단
결과 검수
```

### 1.3 명령어 해석

#### `실행`

- 현재 상태가 `waiting`일 때 분류를 시작한다.
- 입력 리서치 파일의 전체 항목 수를 자동 계산한다.
- Pilot 결과가 20개면 20개만, Full 결과가 200개면 200개 전체를 처리한다.
- 이미 분류된 ID는 덮어쓰지 않고 미완료 ID부터 처리한다.

#### `일시정지`

- 새 사이트 분류를 시작하지 않는다.
- 현재 처리 중인 ID의 점수 근거와 임시 결과를 저장한다.
- `classification/progress.txt`에 `RUN_STATE: paused`를 기록한다.

#### `재개`

- `RUN_STATE: paused`일 때만 허용한다.
- 기존 결과와 진행 상태를 읽고 미완료 ID부터 이어서 처리한다.
- 완료된 ID의 점수와 분류를 임의로 재계산하지 않는다.

#### `중단`

- 신규 분류와 점수 계산을 즉시 중단한다.
- 현재까지의 결과를 저장하고 `RUN_STATE: stopped`를 기록한다.
- 다시 시작하려면 사용자가 파일과 결과를 검토한 뒤 `실행`을 입력한다.

#### `결과 검수`

- 외부 웹에 접근하지 않는다.
- `classification/REFERENCE_CLASSIFICATION.md`와 `classification/DUPLICATE_GROUPS.md`를 대상으로 수량, 중복 그룹, 대표 사이트, 점수 합계, 분류 기준, 우선순위, 근거 연결, 최종 추천 목록을 검사한다.
- 결과를 `classification/validation-report.txt`에 저장한다.
- 검수 과정에서 점수나 분류를 자동 수정하지 않는다.

## 2. 입력 파일과 처리 범위

### 2.1 필수 입력

```text
research/REFERENCE_RESEARCH.txt
research/progress.txt
```

### 2.2 선택 입력

```text
research/unresolved-sites.txt
```

### 2.3 처리 수량

- 입력 수량을 파일에서 자동 계산한다.
- Pilot 분류: 현재 완료된 20개 리서치 항목
- Full 분류: 누적 완료된 200개 리서치 항목
- 분류 대상 수량을 임의로 20개 또는 200개로 가정하지 않는다.
- 실제 입력 항목 수와 `progress.txt`의 수량이 다르면 분류를 시작하지 않고 검수 오류로 기록한다.

### 2.4 읽기 전용 원칙

- `research/` 폴더의 파일은 읽기 전용으로 취급한다.
- 분류 결과는 `classification/REFERENCE_CLASSIFICATION.md`, 중복 그룹 결과는 `classification/DUPLICATE_GROUPS.md`에 새로 저장한다.
- 리서치 원본의 문구, URL, P번호, 상태값을 수정하지 않는다.

## 3. 분류 전 입력 검수

분류 시작 전에 각 사이트 항목을 아래 기준으로 검사한다.

### 3.1 필수 항목

- 수집 ID
- 브랜드명
- 발견 URL 또는 최종 URL
- URL 상태
- 조사 상태
- 확인 페이지 P1 이상
- 주요 관찰 항목
- 관찰 근거 P번호

### 3.2 입력 검수 상태

각 사이트에 다음 중 하나를 부여한다.

```text
validation_pass
validation_partial
validation_duplicate
validation_hold
```

#### `validation_pass`

- 조사 상태가 `completed`
- 최소 P1, P2, P3 확인
- 주요 관찰에 근거 P번호가 연결됨
- 점수 계산에 필요한 정보가 충분함

#### `validation_partial`

- 조사 상태가 `partial`
- 일부 관찰이 `not_verified`
- 최소 2개 페이지와 핵심 관찰 근거가 존재함
- 제한된 범위에서 점수 계산 가능

#### `validation_duplicate`

- 다른 항목과 동일한 공식 사이트 또는 실질적으로 동일한 지역·언어 변형으로 확정됨
- 해당 항목이 중복 그룹의 대표 사이트가 아닌 `duplicate_secondary`임
- 세부 점수와 YOVIA 적합도 분류를 새로 계산하지 않음
- `최종 분류: 중복 제외`, `우선순위: DUPLICATE`로 기록함
- 반드시 `중복 그룹 ID`, `대표 사이트 ID`, `중복 유형`, `중복 판정 근거`를 기록함

#### `validation_hold`

다음 중 하나에 해당하면 점수와 최종 분류를 부여하지 않는다.

- 조사 상태가 `failed`
- URL 상태가 `dead`, `blocked`, `unverified`이며 관찰 자료가 부족함
- 중복 가능성은 있으나 대표·중복 관계를 확정할 근거가 부족함
- 확인 페이지가 1개 이하
- 주요 관찰에 P번호 근거가 없음
- 동일 ID가 중복됨
- 사이트 항목이 심하게 누락됨

`validation_hold`는 `불필요` 분류가 아니다. 근거 부족으로 판정을 보류한 검수 상태다.

## 4. 중복 사이트 판정 및 분류

중복 판정은 점수 계산보다 먼저 수행한다. 외부 웹을 다시 열지 않고, 리서치 파일에 기록된 브랜드명, 발견 URL, 최종 URL, URL 상태, 확인 페이지, 관찰 내용만 사용한다.

### 4.1 중복 상태값

각 사이트에 다음 중 하나를 부여한다.

```text
unique
duplicate_primary
duplicate_secondary
duplicate_candidate
related_not_duplicate
```

#### `unique`

- 다른 입력과 브랜드·공식 도메인·콘텐츠가 중복되지 않는 독립 사이트
- 일반 검수와 점수 계산을 진행함

#### `duplicate_primary`

- 하나의 중복 그룹에서 대표로 유지되는 사이트
- 일반 검수와 A~E 점수 계산을 진행함
- 최종 추천 후보가 될 수 있음

#### `duplicate_secondary`

- 대표 사이트와 동일하거나 실질적으로 같은 사이트로 확정된 중복 항목
- `validation_duplicate`를 부여함
- 별도 점수, P1~P5 우선순위, 최종 추천 자격을 부여하지 않음
- `최종 분류: 중복 제외`, `우선순위: DUPLICATE`로 기록함

#### `duplicate_candidate`

- 중복 가능성이 있으나 리서치 자료만으로 확정할 수 없는 항목
- `validation_hold`, `최종 분류: 미분류`, `우선순위: HOLD`로 기록함
- 추정만으로 대표 사이트나 중복 제외 사이트를 정하지 않음

#### `related_not_duplicate`

- 같은 기업, 유사한 브랜드명, 같은 제품군 또는 비슷한 템플릿을 사용하지만 독립적인 브랜드·사이트 경험으로 판단되는 항목
- 중복으로 제외하지 않고 일반 점수 계산을 진행함

### 4.2 중복 유형

중복으로 판정할 때 다음 유형 중 하나를 기록한다.

```text
exact_url_duplicate
canonical_domain_duplicate
same_brand_page_duplicate
same_brand_region_duplicate
same_brand_language_duplicate
redirect_duplicate
possible_duplicate
not_duplicate
```

- `exact_url_duplicate`: 정규화한 최종 URL이 동일함
- `canonical_domain_duplicate`: 경로나 추적값은 다르지만 동일한 공식 대표 도메인임
- `same_brand_page_duplicate`: 동일 브랜드의 홈·제품 상세 URL이 별도 사이트처럼 중복 수집됨
- `same_brand_region_duplicate`: 동일 브랜드의 국가별 사이트이며 구조·콘텐츠·역할이 실질적으로 같음
- `same_brand_language_duplicate`: 언어만 다르고 사이트 구조와 핵심 콘텐츠가 동일함
- `redirect_duplicate`: 서로 다른 발견 URL이 같은 최종 공식 URL로 리디렉션됨
- `possible_duplicate`: 중복 가능성만 확인되어 확정할 수 없음
- `not_duplicate`: 검토 결과 독립 사이트로 확인됨

### 4.3 URL 정규화 규칙

중복 비교용 URL은 다음 순서로 정규화한다.

1. `최종 URL`이 있으면 발견 URL보다 우선함
2. 프로토콜(`http`, `https`) 차이를 제거함
3. `www.` 차이를 제거함
4. 호스트명을 소문자로 변환함
5. 끝 슬래시, 프래그먼트, 추적용 쿼리 파라미터를 제거함
6. 홈 URL과 동일 사이트의 대표 제품 URL은 브랜드명과 페이지 역할을 함께 비교함
7. URL 문자열만 같다는 이유로 서로 다른 브랜드를 하나로 합치지 않음

### 4.4 중복 확정 조건

다음 중 하나가 리서치 근거로 확인되면 중복 그룹을 만들 수 있다.

- 정규화한 최종 URL이 동일함
- 서로 다른 입력 URL이 같은 공식 최종 URL로 이동함
- 브랜드명과 공식 대표 도메인이 같고 하나는 홈, 하나는 하위 제품 페이지임
- 동일 브랜드의 국가·언어 변형이며 IA, 핵심 콘텐츠, 제품 역할이 실질적으로 같음
- 리서치 관찰 내용이 동일하고 독립 브랜드로 볼 근거가 없음

다음은 중복으로 처리하지 않는다.

- 같은 모기업이지만 브랜드명이 다름
- 같은 카테고리나 제품 유형임
- 디자인 템플릿 또는 기능이 유사함
- 동일 브랜드의 지역 사이트라도 제품군, IA, 콘텐츠, 사용자 흐름이 실질적으로 다름
- 브랜드명은 비슷하지만 공식 도메인과 운영 주체가 다름

### 4.5 대표 사이트 선정 규칙

중복 그룹마다 정확히 하나의 `duplicate_primary`를 선정한다. 아래 순서를 기계적으로 적용한다.

1. `validation_pass` 우선
2. 조사 상태 `completed` 우선
3. URL 상태 `active` 또는 `redirected` 우선
4. 확인 페이지 수와 P번호 근거가 더 많은 항목 우선
5. 브랜드의 공식 루트 또는 대표 도메인 우선
6. 모바일·제품 목록·제품 상세 관찰이 더 완전한 항목 우선
7. 모든 조건이 같으면 수집 ID가 작은 항목 우선

대표 사이트 선정 이유를 최소 2개 기록한다. 대표가 아닌 항목은 모두 `duplicate_secondary`로 처리한다.

### 4.6 중복 그룹 형식

중복 그룹 ID는 `DUP-001`, `DUP-002` 형식으로 부여한다.

```markdown
## DUP-001

- 대표 사이트: 001 브랜드명
- 대표 URL:
- 대표 선정 이유:
- 중복 유형:
- 포함 ID: 001, 014, 019
- 중복 제외 ID: 014, 019
- 판정 근거:
- 확정 수준: confirmed / candidate
```

상세 중복 그룹은 `classification/DUPLICATE_GROUPS.md`에 저장하고, 메인 분류 결과에도 각 사이트의 중복 상태와 대표 ID를 기록한다.

## 5. 분류 카테고리

YOVIA 적합도 최종 분류는 아래 세 가지다. 이 세 분류는 `unique`, `duplicate_primary`, `related_not_duplicate` 중 점수 계산이 가능한 항목에만 적용한다. `duplicate_secondary`는 별도 상태인 `중복 제외`, `duplicate_candidate`는 `미분류`로 처리한다.

```text
핵심 필요
부분 참고
불필요
```

### 5.1 핵심 필요

YOVIA 웹사이트의 전체 방향 또는 주요 화면 설계에 직접적인 기준으로 사용할 가치가 높은 사이트다.

필수 조건:

- 총점 75점 이상
- YOVIA 제품·타깃 적합도 12점 이상
- 디자인 적합도 15점 이상
- UX 적합도 15점 이상
- 근거 품질 5점 이상
- `validation_pass` 또는 충분한 `validation_partial`

다음 중 두 가지 이상이 구체적으로 확인되어야 한다.

- 식품·요거트·휴대형 제품과 직접 연결되는 제품 표현
- YOVIA의 올인원 패키지 또는 사용 과정 설명에 적용 가능한 구조
- 바쁜 20~30대 사용 맥락과 연결되는 메시지 구성
- 메인 페이지, 제품 목록, 상세 페이지에 적용 가능한 명확한 UX
- 모바일에서 활용 가능한 콘텐츠 흐름
- 패키지·질감·토핑을 중심으로 한 시각적 제품 연출

### 5.2 부분 참고

사이트 전체가 YOVIA에 직접 맞지는 않지만 특정 요소를 선별해 참고할 가치가 있는 사이트다.

다음 중 하나에 해당한다.

- 총점 50~74점
- 총점이 50점 미만이어도 디자인 적합도 20점 이상
- 총점이 50점 미만이어도 UX 적합도 20점 이상
- 총점이 50점 미만이어도 제품·타깃 적합도 16점 이상
- 특정 화면, 콘텐츠 표현, 인터랙션, 패키지 연출 중 하나가 뚜렷함

부분 참고로 분류할 때는 반드시 참고 범위를 제한해서 기록한다.

예:

```text
히어로 비주얼만 참고
모바일 상품 상세 흐름만 참고
사용 방법 설명 섹션만 참고
맛별 컬러 구분 방식만 참고
```

### 5.3 불필요

검수 가능한 자료는 있으나 YOVIA 웹사이트 기획에 직접 적용할 요소가 매우 적은 사이트다.

조건:

- 총점 50점 미만
- 디자인 적합도 20점 미만
- UX 적합도 20점 미만
- 제품·타깃 적합도 16점 미만
- 고유하게 참고할 단일 요소도 명확하지 않음

다음 이유만으로 불필요 판정을 내려서는 안 된다.

- 개인 취향에 맞지 않음
- 색상이 YOVIA와 다름
- 해외 사이트임
- 제품군이 완전히 동일하지 않음
- 구현 난도가 높음

## 6. 100점 평가 기준

총점은 100점이다.

```text
A. YOVIA 제품·타깃 적합도: 20점

합계: 100점
```

각 세부 항목은 0~5점으로 평가한다.

### 6.1 공통 0~5점 기준

```text
0점: 확인 불가 또는 관련성 없음
1점: 매우 약한 관련성
2점: 제한적 관련성
3점: 일부 적용 가능
4점: 높은 적용 가능성
5점: 직접적인 기준으로 활용 가능
```

점수에는 반드시 리서치 파일의 P번호 근거를 연결한다.

## 15. 최종 추천 사이트 선정

### 15.1 추천 수량

```text
Pilot 20개 분류: 최대 5개
Full 200개 분류: 최대 15개
```

### 15.2 추천 자격

- P1 또는 P2
- `validation_pass` 또는 충분한 `validation_partial`
- 총점 75점 이상
- 중복 상태가 `unique`, `duplicate_primary`, `related_not_duplicate` 중 하나임
- 추천 이유가 최소 3개 이상 존재
- 각 추천 이유에 P번호 근거가 연결됨

### 15.3 역할별 추천

최종 추천 목록은 가능한 경우 다음 역할을 균형 있게 포함한다.

```text
전체 디자인 기준
메인·IA·UX 기준
제품 상세·사용법 기준
모바일·반응형 기준
패키지·제품 비주얼 기준
```

한 사이트가 여러 역할을 담당할 수 있다. 단, 동일 중복 그룹에서는 `duplicate_primary` 한 개만 추천할 수 있으며 `duplicate_secondary`와 `duplicate_candidate`는 추천하지 않는다.

### 15.4 추천 결과에 포함할 내용

사이트마다 다음을 기록한다.

- 추천 순위
- 브랜드명과 URL
- 총점과 우선순위
- 추천 역할
- YOVIA에 적용 가능한 요소 3개
- 그대로 복제하면 안 되는 요소 또는 주의점 1~2개
- 근거 P번호

## 19. 검수 규칙

### 19.1 입력 검수

- [ ] 입력 리서치 파일이 존재한다.
- [ ] 중복 항목이 있으면 `classification/DUPLICATE_GROUPS.md`가 생성되었다.
- [ ] 입력 사이트 수와 `progress.txt` 수량이 일치한다.
- [ ] 모든 사이트 ID가 고유하다.
- [ ] 모든 사이트에 URL과 조사 상태가 있다.
- [ ] 모든 사이트에 중복 상태가 있다.
- [ ] 중복 그룹마다 대표 사이트가 정확히 1개다.
- [ ] `duplicate_secondary`에 대표 사이트 ID와 중복 근거가 있다.
- [ ] `duplicate_candidate`가 추정만으로 중복 제외되지 않았다.
- [ ] `validation_hold` 사유가 명확하다.

### 19.2 점수 검수

- [ ] 모든 세부 점수가 허용 범위 안에 있다.
- [ ] A 합계가 20점을 초과하지 않는다.
- [ ] B 합계가 25점을 초과하지 않는다.
- [ ] C 합계가 25점을 초과하지 않는다.
- [ ] D 합계가 20점을 초과하지 않는다.
- [ ] E 합계가 10점을 초과하지 않는다.
- [ ] 총점이 A+B+C+D+E와 일치한다.
- [ ] 점수 근거가 P번호와 연결되어 있다.
- [ ] `not_verified` 항목을 확인된 사실처럼 점수화하지 않았다.

### 19.3 분류 검수

- [ ] 핵심 필요 사이트가 필수 최소 점수를 충족한다.
- [ ] 부분 참고 사이트에 구체적인 참고 범위가 있다.
- [ ] 불필요 사이트가 근거 부족이 아닌 낮은 적합도로 판정되었다.
- [ ] `validation_hold`를 불필요로 처리하지 않았다.
- [ ] `validation_duplicate`를 불필요 또는 HOLD로 잘못 처리하지 않았다.
- [ ] 중복 대표 사이트만 일반 점수와 분류를 받았다.
- [ ] 총점과 분류 기준이 충돌하지 않는다.

### 19.4 우선순위 검수

- [ ] P1은 85점 이상 핵심 필요다.
- [ ] P2는 75~84점 핵심 필요다.
- [ ] P3과 P4는 부분 참고다.
- [ ] P5는 불필요다.
- [ ] DUPLICATE는 중복 제외다.
- [ ] HOLD와 DUPLICATE는 순위 계산에서 제외했다.
- [ ] 동점 처리 규칙을 적용했다.

### 19.5 최종 추천 검수

- [ ] Pilot은 최대 5개, Full은 최대 15개다.
- [ ] 추천 사이트는 P1 또는 P2다.
- [ ] 동일 중복 그룹에서 대표 사이트만 추천되었다.
- [ ] `duplicate_secondary`와 `duplicate_candidate`가 추천 목록에 없다.
- [ ] 역할별 참고 범위가 명확하다.
- [ ] 추천 이유가 최소 3개다.
- [ ] 모든 추천 이유에 P번호 근거가 있다.
- [ ] 복제 금지 또는 변환 주의점이 포함되어 있다.

### 19.6 중복 검수

- [ ] URL 정규화 규칙을 일관되게 적용했다.
- [ ] 같은 모기업 또는 같은 카테고리라는 이유만으로 중복 처리하지 않았다.
- [ ] 중복 그룹마다 `duplicate_primary`가 정확히 1개다.
- [ ] 모든 `duplicate_secondary`가 하나의 대표 사이트를 가리킨다.
- [ ] 대표 선정 규칙과 대표 선정 이유가 기록되어 있다.
- [ ] 중복 제외 항목에 점수와 P1~P5 우선순위를 부여하지 않았다.
- [ ] `duplicate_candidate`는 HOLD로 유지했다.
- [ ] `DUPLICATE_GROUPS.md`의 그룹 수와 메인 결과의 중복 수가 일치한다.

### 19.7 수량 검수

다음 수식이 성립해야 한다.

```text
입력 사이트 수 = 핵심 필요 + 부분 참고 + 불필요 + 중복 제외 + HOLD
```

다음 수식도 성립해야 한다.

```text
핵심 필요 = P1 + P2
부분 참고 = P3 + P4
불필요 = P5
중복 제외 = DUPLICATE = duplicate_secondary
판정 보류 = HOLD
```

## 22. 최종 실행 지시

이 문서를 읽은 에이전트는 다음 순서로 작업한다.

1. 입력 명령이 `실행`, `일시정지`, `재개`, `중단`, `결과 검수` 중 무엇인지 판별한다.
2. `결과 검수`이면 외부 웹에 접근하지 않고 기존 분류 결과만 검사한다.
3. `실행` 또는 허용된 `재개`이면 `research/REFERENCE_RESEARCH.txt`와 `research/progress.txt`를 읽는다.
4. 입력 사이트 수와 완료 상태를 검수한다.
5. URL과 브랜드 정보를 정규화하고 사이트별 중복 상태를 판정한다.
6. 중복 그룹마다 대표 사이트 1개를 선정하고 `classification/DUPLICATE_GROUPS.md`에 기록한다.
7. 사이트별로 `validation_pass`, `validation_partial`, `validation_duplicate`, `validation_hold`를 판정한다.
8. `duplicate_primary`, `unique`, `related_not_duplicate` 중 HOLD가 아닌 항목만 A~E 기준으로 점수화한다.
9. `duplicate_secondary`는 `중복 제외 / DUPLICATE`, `duplicate_candidate`는 `미분류 / HOLD`로 처리한다.
10. 총점과 최소 조건을 함께 적용해 대표·고유 사이트를 `핵심 필요`, `부분 참고`, `불필요`로 분류한다.
11. 점수와 분류에 따라 P1~P5 우선순위를 부여한다.
12. 모든 판단에 리서치 파일의 P번호 근거를 연결한다.
13. 사이트별 고정 출력 양식으로 `classification/REFERENCE_CLASSIFICATION.md`에 저장한다.
14. 전체 분류 완료 후 동점 처리 규칙에 따라 순위를 정한다.
15. Pilot이면 최대 5개, Full이면 최대 15개의 최종 추천 사이트를 선정한다.
16. 분류·중복·점수·추천 결과에 대해 검수 규칙을 모두 수행한다.
17. 검수 결과를 `classification/validation-report.txt`에 저장한다.
18. 검수 통과 시 `classification/progress.txt`에 `RUN_STATE: completed`를 기록한다.
19. 검수 실패 시 결과를 임의 수정하지 않고 오류 보고서를 저장한 뒤 종료한다.
